# Catalyst Deployment Guide

How to deploy the `doc_compare` Catalyst Advanced I/O function, and the gotchas
that aren't obvious from Zoho's own docs. Read this before your first deploy on
a new machine, and the Changelog at the bottom before touching auth, DataStore,
or parallelism code — those were all wrong in ways that only show up at runtime.

---

## 1. Prerequisites

```bash
npm install -g zcatalyst-cli
catalyst login
```

From the repo root:

```bash
catalyst project:use
# select "Project-Rainfall"
```

This writes `.catalystrc` (project/environment linkage — machine-local, not
secret, regenerated by this command, gitignored).

---

## 2. Environment variables — read this before your first deploy

**Do not set these only in the Catalyst Console.** `catalyst deploy` pushes
`functions/doc_compare/catalyst-config.json`'s `env_variables` field to the
Console and it becomes the new source of truth for the function — every deploy
overwrites whatever was typed into the Console with what's in that file. If you
only ever set values in the Console, the next `catalyst deploy` silently wipes
them back to nothing and you'll be re-typing them forever.

The file is tracked in git with `env_variables: {}` (a safe empty placeholder —
we do not commit real secrets), but your **local working copy** needs the real
values so every deploy pushes them automatically. One-time setup per machine:

```bash
git update-index --skip-worktree functions/doc_compare/catalyst-config.json
```

This tells git to stop watching *your local copy* of that one file for changes.
The committed version stays the safe placeholder; your local edits (real
secrets) never show up in `git status`, never get diffed, never get committed.

Then edit your local copy and fill in:

| Key | Where it comes from |
|---|---|
| `CLAUDE_API_KEY` | Anthropic console |
| `GEMINI_API_KEY` | Google AI Studio |
| `PPO_PDF_FIELD` | default `PARTNER_PO_PDF` — leave as-is unless the CRM field API name changed |
| `VQ_PDF_FIELD` | default `VQ_PDF` — leave as-is unless the CRM field API name changed |
| `CLIENT_ID` | Zoho OAuth self-client at [api-console.zoho.com](https://api-console.zoho.com) |
| `CLIENT_SECRET` | same self-client |
| `REFRESH_TOKEN` | generated from that self-client, scopes `ZohoCRM.modules.ALL` + `ZohoCRM.files.ALL` |

`CLIENT_ID`/`CLIENT_SECRET`/`REFRESH_TOKEN` are the **same category of credential
the old Cloud Run `app.py` used** — if you still have those values, reuse them,
they already carry the right scopes. Do NOT rely on Catalyst's own
`context.credential.token()` for Zoho CRM API calls — it authenticates you to
Catalyst's own services (DataStore/Cache/Filestore) only, and has no CRM API
scope. See `CLAUDE.md`'s "Zoho CRM auth" section for the full story (confirmed
live via a `401 OAUTH_SCOPE_MISMATCH` error — this isn't theoretical).

Verify the skip-worktree took effect:

```bash
git status --short   # catalyst-config.json should NOT appear, even after editing it
```

To undo skip-worktree later (e.g. handing the project to CI, which needs its
own env var mechanism instead): `git update-index --no-skip-worktree functions/doc_compare/catalyst-config.json`.

**Different data center?** If the CRM org isn't on the US DC, also set
`ZOHO_ACCOUNTS_URL` (e.g. `https://accounts.zoho.eu`) — `main.py` defaults to
`https://accounts.zoho.com`.

## 3. Deploying

```bash
catalyst deploy --only functions:doc_compare
```

Or deploy everything in the project: `catalyst deploy`.

---

## 4. Checking logs

`catalyst logs:get` is **not a real command** in the current CLI (v1.27.0,
confirmed against `catalyst --help` — it's not in the command list). View logs
in the Catalyst Console instead: **Console → your project → Functions →
doc_compare → Logs**. That's where every error in this file's Changelog below
was actually diagnosed from.

---

## 5. Testing locally before deploying

```bash
catalyst serve
```

Serves Basic I/O and Advanced I/O functions locally. Useful for catching syntax
errors before burning a deploy cycle, though it can't fully replicate Catalyst's
production request/credential/DataStore environment — several of the bugs in
the Changelog below only showed up once actually deployed.

---

## 6. Widget-side config

The CRM widget (`index.html`, uploaded directly via Zoho CRM → Setup →
Developer Space → Widgets, not deployed via Catalyst — see `CLAUDE.md`) has its
own `BASE_URL` pointing at this function's deployed URL. If you rename the
Catalyst project or function, update it there too.

## Changelog

Deployment- and runtime-compatibility-affecting changes, most recent first.
Add an entry here whenever a change would otherwise surprise the next person
deploying this function — not routine feature work, just things that change
*how deployment/auth/runtime behaves*.

### 2026-08-26 — Migrated off Cloud Run to Catalyst; fixed six runtime-compatibility bugs + one deploy-config footgun

The Catalyst port (`main.py`, replacing Cloud Run's `app.py`) was written
against an imagined SDK surface that didn't match `zcatalyst-sdk==1.4.0`'s real
API. All of the following were found live, one redeploy at a time, and fixed:

1. **`request.catalyst` doesn't exist.** `request` is a real Flask `Request` —
   get the Catalyst context via `zcatalyst_sdk.initialize()` inside `handler()`.
2. **`request.body` doesn't exist** (Flask `Request` has no such attribute) —
   use `request.get_data(as_text=True)`.
3. **`catalyst.response()` doesn't exist** (that package isn't even installed) —
   responses go back via Flask's `make_response(jsonify(body), status)`.
4. **`context.get_token()` doesn't exist** on `CatalystApp`, AND
   `context.credential.token()` (the thing that does exist) is scoped to
   Catalyst's own services, not the CRM API — confirmed via a live `401
   OAUTH_SCOPE_MISMATCH`. Restored the original Cloud Run refresh-token OAuth
   flow (`CLIENT_ID`/`CLIENT_SECRET`/`REFRESH_TOKEN`, cached module-level) —
   see §2 above.
5. **DataStore `Table` API misuse** — `table.update_row(criteria, data)` and
   `table.get_rows({...})` don't exist; Catalyst rows are addressed by a system
   `ROWID`, not by arbitrary columns. Reads now go through
   `context.zcql().execute_query("SELECT * FROM CompareJobs WHERE job_id = '...'")`;
   writes look up the `ROWID` first, then `update_row({"ROWID": ..., **fields})`.
6. **`concurrent.futures.ThreadPoolExecutor` crash**: `RuntimeError: cannot
   schedule new futures after interpreter shutdown`. That module keeps one
   atexit hook shared by every executor in the process; once it fires (a
   prior/abandoned invocation's worker teardown, on Catalyst's warm-process
   reuse), it permanently breaks `.submit()` for the rest of that worker's
   life — unrelated new requests included. **Not a "Catalyst disallows
   threading" restriction** — swapped to a small `_run_parallel()` helper using
   raw `threading.Thread`, which has no such shared flag. Same real
   parallelism, same latency, no fragility.
7. **Env vars getting wiped on every deploy** (not a code bug — a deploy-config
   footgun): `catalyst-config.json`'s `env_variables` field is pushed to the
   Console on every `catalyst deploy` and becomes the new source of truth,
   silently overwriting anything typed into the Console by hand. Fixed via
   `git update-index --skip-worktree` on that file — see §2 above.
8. **`generated_at` write rejected**: `[DataStore] write error: INVALID_INPUT
   ... datetime value expected`. `CompareJobs.generated_at` is a real Catalyst
   `Datetime` column, not text as originally assumed — it rejects Python's
   `datetime.now().isoformat()` (has a `T`, fractional seconds, no space).
   Catalyst `Datetime` columns want `"YYYY-MM-DD HH:MM:SS"` exactly — fixed via
   `datetime.now().strftime("%Y-%m-%d %H:%M:%S")`, confirmed against Zoho's own
   column-type docs (`docs.catalyst.zoho.com/en/cloud-scale/help/data-store/columns`).
9. **`Worker was sent SIGKILL! Perhaps out of memory?`** — not a code bug, a
   resource-allocation one. The default 256MB is too small for this function's
   dependency footprint (`google-generativeai` alone pulls in a heavy
   grpc/protobuf/cryptography chain, plus `anthropic` and in-memory PDF
   buffers). Fix: `catalyst functions:config doc_compare --memory 512` (bump
   further if it recurs). A `SIGKILL` can't be caught by Python, so when this
   happens mid-request the job's DataStore row simply stops being updated — the
   widget isn't desynced, it's accurately showing the last phase written before
   the worker died. Fixing the OOM resolves both symptoms at once.

All fixes verified against the real installed `zcatalyst-sdk` source (not just
docs, which are incomplete/inconsistent in places) and exercised with mocked
unit tests before deployment. See `CLAUDE.md` for the full technical writeup of
each ("Zoho CRM auth", "Catalyst DataStore", "Common issues & fixes", "What NOT
to change" sections).
